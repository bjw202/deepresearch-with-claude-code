## 2. Researcher 산출물 요약

### R1: wiki-llm 핵심 개념 + 아키텍처 분석 (web) — 완료

- **3줄 요약**:
  1. wiki-llm은 3계층(Raw Sources → Wiki → Schema) + 3오퍼레이션(Ingest/Query/Lint)으로 구성된 "지식 컴파일러" 패러다임. RAG와의 핵심 차이는 질의마다 재발견이 아닌 수집 시 한 번 컴파일 후 영속 축적이다.
  2. GraphRAG와는 대립이 아닌 보완 관계("가까운 친척"). 개인/소규모 팀: wiki-llm 우위, 기업 규모·보안: GraphRAG·시멘틱DB 우위라는 규모별 분기점이 도출됐다.
  3. 핵심 미검증 전제: Lint 오퍼레이션의 환각 감지 정확도 벤치마크 없음. 수천\~수백만 문서 규모에서의 스케일링 한계 미확인.
- **핵심 수치**:
  - Karpathy 사례: \~100기사, 400,000단어 (Karpathy 직접 작성 0자) \[VentureBeat, ★★☆\]
  - 온톨로지 엔지니어 대체 비용: $107K–$207K/year \[Pebblous, ★★☆\]
  - 기업용 KG 구축 비용: $10M–$20M → wiki-llm은 API 비용만 \[Pebblous, ★★☆\]
  - RAG 신규 사실 정확도: 0.875 \[Pebblous 벤치마크, ★☆☆\]
- **검색 비용**: WebSearch 2회, WebFetch 3회, search.sh 0회 (합계 5회 / 22회 상한)
- **편향 주의**: Epsilla(이해관계사) 비판은 ★☆☆ 하향 적용
- **완료 시점**: 2026-04-08

### R2: 온톨로지/KG/GraphRAG 학술 현황 + wiki-llm 대체 가능성 (academic) — 완료

- **3줄 요약**:
  1. GraphRAG는 단순 팩트 쿼리(NQ F1: 65.44% vs RAG 68.18%, -3.7%p 열세)에서 RAG에 뒤지지만, 다중 홉 쿼리(MultiHop-RAG: 71.17% vs 65.77%, +8.3%p 우위)에서 역전된다. 쿼리 유형별 적용 경계가 명확히 존재.
  2. 온톨로지 기반 KG + 청크 통합 시 GraphRAG와 동등한 90% 정확도 달성(vs Vector RAG 60%). 단, 온톨로지 자동 구축은 논리적 일관성·환각 억제 미해결로 전문가 검토 없는 완전 자동화 불가.
  3. LazyGraphRAG(2025-06)가 돌파구: 인덱싱 비용을 Full GraphRAG의 0.1% 수준으로 감소. wiki-llm 100K 토큰 한계는 컨텍스트 윈도우 확장에 따라 이동하는 변수이므로 절대적 한계가 아님.
- **핵심 수치**:
  - NQ 단순 쿼리: RAG F1 68.18% vs GraphRAG 65.44% (RAG 우위) \[arXiv:2502.11371, ★★★\]
  - MultiHop 쿼리: GraphRAG 71.17% vs RAG 65.77% (GraphRAG 우위) \[arXiv:2502.11371, ★★★\]
  - Onto-KG + 청크 정확도: 90% (GraphRAG 동등) vs Vector RAG 60% \[arXiv:2511.05991, ★★☆\]
  - GraphRAG 인덱싱 비용: $50\~200/1K문서 → LazyGraphRAG: \~$0.02\~0.05 \[aithinkerlab, ★☆☆\]
- **검색 비용**: WebSearch 3회, WebFetch 4회, search.sh 3회 (합계 10회 / 22회 상한)
- **완료 시점**: 2026-04-08

### R3: 시멘틱 DB + 현업 활용 시나리오 (web) — 완료

- **3줄 요약**:
  1. 벡터 DB 시장은 성숙 단계 진입($2.2B→$10.6B, CAGR 27.5%). 업계 컨센서스는 "벡터+그래프+시멘틱 레이어" 다층 아키텍처로 이동 중이며, 순수 벡터 검색의 한계를 공식 인정하는 흐름이다.
  2. wiki-llm 스위트 스팟은 50,000\~100,000 토큰 이하(\~150-200 페이지)로 명확히 한계 확인. 이를 초과 시 오히려 RAG보다 비용 증가. 규제 산업·수만 문서 이상 환경에는 절대 부적합.
  3. 추천 하이브리드: wiki-llm(안정적·큐레이션된 지식 → 시스템 프롬프트) + RAG(동적·대규모 문서 → 벡터 검색) 병행이 현실적 최적 경로.
- **핵심 수치**:
  - 벡터 DB 시장: $2.2B(2024) → $10.6B(2032), CAGR 27.5% \[firecrawl.dev, ★★☆\]
  - LLM + 시멘틱 레이어 정확도 향상: 최대 300% \[AtScale 자사 발표, ★☆☆ — 이해당사자\]
  - wiki-llm 거버넌스 레이어 비용: RAG 인프라 대비 +20-30% \[NStarX/Atlan, ★★☆\]
  - GraphRAG LinkedIn 사례: 티켓 해결 시간 40h → 15h (63% 개선) \[VentureBeat, ★★★\]
  - wiki-llm 스위트 스팟: 50,000\~100,000 토큰 이하 (\~150-200 페이지)
- **검색 비용**: WebSearch 4회, WebFetch 3회(1회 429 오류), search.sh 2회 (합계 9회 / 22회 상한)
- **완료 시점**: 2026-04-08

## 6. 후속 리서치 시드

1. **wiki-llm Ingest TCO 정량화** — 쿼리 시 절감만이 아닌, Ingest+Lint 사전 컴파일 비용 포함 총소유비용 비교 (R1·R3에서 제기, Critic이 누락 확인)
2. **Lint 오퍼레이션 환각 감지 정확도 벤치마크** — wiki-llm의 장기 신뢰성 전제이나 2026-04 기준 실증 연구 없음 (R1에서 제기)
3. **컨텍스트 윈도우 확장에 따른 wiki-llm vs GraphRAG 역전점** — 1M 토큰 이상 윈도우에서 GraphRAG 존재 이유가 "다중 홉 추론"만으로 축소되는지 (R2에서 제기)
4. **wiki-llm vs Notion AI / Confluence AI 직접 비교** — 실제 기업 PKM 경쟁 구도에서의 위치 (Critic에서 제기)
5. **LLM Git merge conflict 자율 해결 가능성** — wiki-llm 멀티유저 확장의 핵심 병목 (R3에서 제기)
